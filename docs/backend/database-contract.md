# Database Contract

Wave 11 defines the provider-neutral database contract for the trainer app. It is a documentation artifact for future backend work and must stay aligned with the current local domain types, Wave 9 API boundary, and Wave 10 auth shell.

This document uses relational table names for clarity. A document database may implement the same contract as collections/subcollections if it preserves the ownership filters, uniqueness rules, indexes, lifecycle fields, and invariants described here.

## Non-Goals

- No backend provider or database engine is selected here.
- No executable migrations, SDK setup, API client implementation, network rollout, auth provider integration, token persistence, route changes, or production hardening are introduced here.
- No app runtime code changes are required by this document.

## Source Contracts

- Domain IDs are stable strings: `ClientId`, `ExerciseId`, `WorkoutId`, `SessionId`, `ResultId`, and `QuickValueId`.
- `OwnerId` is currently a string. Development auth maps signed-in state to `local-trainer`.
- API DTOs use snake_case and carry `owner_id` on owner-scoped records.
- All API mutations require an idempotency key.
- Query responses may use `{ data: T[], next_cursor?: string }` envelopes.
- Result types are `weight_reps`, `reps`, `duration`, and `distance_duration`.

## Ownership Model

Every trainer-owned table must include `owner_id`. Future production identity may introduce `account_id` and `workspace_id`, but those are unresolved blockers.

Required server behavior:

- Resolve the authenticated principal to an allowed owner/workspace before any query or mutation.
- Apply owner/workspace filtering on every read.
- Reject writes that reference entities owned by another owner/workspace.
- Return not-found or forbidden without leaking whether another owner has the referenced ID.
- Preserve owner-scoped local semantics where other-owner entities behave as not found.

Assumption placeholders:

| Concept | Current status | Contract requirement |
| --- | --- | --- |
| `owner_id` | Confirmed app-level scope | Required on clients, exercises, workouts, sessions, results, quick values, settings, and idempotency records. |
| `account_id` | Unknown | Do not require in Wave 12 until auth/account model is decided. |
| `workspace_id` | Unknown | If introduced, it must be part of every authorization check and likely every composite index. |
| `local-trainer` | Development-only | May seed or migrate local data, but must not be treated as a production tenant ID. |

## Common Field Rules

- `id`: stable string generated by the client or server according to the future API decision. Once returned to the app, it must not change.
- `owner_id`: stable string tenant/owner scope.
- `created_at`: UTC ISO timestamp for server-created records. Optional in current DTOs but recommended for backend records.
- `updated_at`: UTC ISO timestamp that changes on material updates. Optional in current DTOs but recommended for sync and conflict checks.
- Timestamps stored by app contracts use UTC ISO strings.
- Timezone fields such as `timezone`, `started_timezone`, and `completed_timezone` use IANA timezone identifiers.
- Soft lifecycle fields such as `archived_at`, `cancelled_at`, and `completed_at` are preferred over destructive deletes for user-facing data.
- Provider credentials, access tokens, refresh tokens, and credential-vault data must not be stored in these domain tables.

| Field | Requirement |

| `name` | Required. |

Lifecycle/status:

- `status` is `active`, `paused`, or `new`.

Ownership references:

- Workouts, sessions, results, and quick values referencing a client must match the same `owner_id`.

### `exercises`

| Field | Requirement |
| --- | --- |
| `id`, `owner_id` | Required stable identity and tenant scope. |
| `name` | Required. |
| `category` | `strength`, `mobility`, or `cardio`. |
| `source` | Optional, currently `built_in` or `custom`. |
| `primary_muscles` | Required string list. |
| `secondary_muscles` | Optional string list. |
| `equipment` | Required string. |
| `coach_notes`, `notes` | Optional strings. |

Lifecycle/status:

- Active exercises have no `archived_at`.
- Archived exercises are excluded from active exercise pickers but must remain readable for historical workouts/results.
- Custom active exercise names should be unique per owner after normalization. Built-in exercise ownership/source rules need provider decision before global library rollout.

### `workouts`

Purpose: planned workout, draft workout, edited workout draft, moved workout, cancelled workout, and completed workout schedule record.

Fields mirror `ApiWorkoutDto`:

| Field | Requirement |
| --- | --- |
| `id`, `owner_id` | Required stable identity and tenant scope. |
| `client_id` | Optional same-owner client reference. |
| `title`, `starts_at`, `duration_minutes`, `focus`, `location`, `status` | Required by current DTO. |
| `timezone` | Optional IANA timezone for scheduled local time context. |
| `source_workout_id` | Optional same-owner workout reference for edit/move lineage. |
| `cancelled_at`, `cancellation_reason` | Optional cancellation lifecycle fields. |
| `repeat_days`, `schedule_times` | Optional recurrence helper fields. |
| `created_at`, `updated_at` | Optional in DTO, recommended in backend. |

Lifecycle/status:

- `status` is `draft`, `planned`, `active`, `inProgress`, `completed`, `cancelled`, or `moved`.
- Draft publishing must be atomic: either the planned workout is created/updated and draft state is resolved, or no visible partial change remains.
- Reschedule/cancel/apply-edit operations must preserve ID references expected by the app contracts.

Relationships:

- `client_id` must belong to the same `owner_id` when present.
- `source_workout_id` must belong to the same `owner_id` when present.
- Child workout exercises/sets are part of the workout aggregate unless the provider requires normalized tables.

### `workout_exercises`

Purpose: exercise items inside a workout. This may be an embedded array in document stores or a normalized child table.

Fields mirror `ApiWorkoutExerciseDto`:

| Field | Requirement |
| --- | --- |
| `id` | Stable item ID within the workout aggregate. |
| `owner_id` | Required if stored as a separate table; inherited from parent if embedded. |
| `workout_id` | Required parent reference if normalized. |
| `exercise_id` | Required same-owner exercise reference. |
| `exercise_name` | Required display name at planning time. |
| `result_type` | Optional result type, defaulting to `weight_reps` when absent. |
| `order`, `day`, `muscle_group`, `comment`, `collapsed`, `superset_with_next` | Optional planning/editor fields. |

Set shape mirrors `ApiWorkoutSetDto`:

| Field | Requirement |
| --- | --- |
| `id`, `order`, `completed` | Required set identity/order/completion. |
| `target_weight_kg`, `target_reps`, `target_duration_seconds`, `target_distance_meters` | Optional targets according to result type. |
| `actual_weight_kg`, `actual_reps`, `actual_duration_seconds`, `actual_distance_meters` | Optional actual values used during editing/session flows. |

Constraints:

- `(owner_id, workout_id, id)` should be unique if normalized.
- `order` must support stable user ordering.
- Superset connections rely on adjacent ordered items and `superset_with_next`.

### `workout_sessions`

Purpose: an execution instance for a workout.

Fields mirror `ApiWorkoutSessionDto`:

| Field | Requirement |
| --- | --- |
| `id`, `owner_id` | Required stable identity and tenant scope. |
| `workout_id` | Required same-owner workout reference. |
| `client_id` | Optional same-owner client reference. |
| `status` | `active`, `completed`, or `cancelled`. |
| `started_at` | Required UTC ISO timestamp. |
| `started_timezone` | Optional IANA timezone. |
| `completed_at`, `completed_timezone`, `duration_seconds` | Optional completion lifecycle fields. |
| `workout_title_snapshot` | Optional stable title snapshot for history. |
| `created_at`, `updated_at` | Optional in DTO, recommended in backend. |

Active-session invariant:

- There may be at most one `active` workout session per `owner_id`.
- Starting the same workout while its session is already active should return the existing active session.
- Starting a different workout while another session is active should fail with an active-session conflict that includes enough existing-session data for the app to route to that session.
- Completing a session must be idempotent. Repeating completion for an already completed session should return the completed session rather than creating duplicate history.
- The invariant must be enforced by the backend, not only by the client.

Recommended physical constraint:

- For relational databases, use a partial unique index equivalent to `unique(owner_id) where status = 'active'`.
- For document databases without partial unique indexes, use a per-owner active-session lock/sentinel document updated transactionally with session start/complete.

### `workout_results`

Purpose: recorded set result for a session exercise.

Fields mirror `ApiWorkoutResultDto`:

| Field | Requirement |
| --- | --- |
| `id`, `owner_id` | Required stable identity and tenant scope. |
| `session_id` | Required same-owner session reference. |
| `session_exercise_item_id` | Optional session exercise item reference; recommended for disambiguation. |
| `exercise_id` | Required same-owner exercise reference. |
| `exercise_name_snapshot` | Optional history snapshot. |
| `result_type` | Optional result type; default to session/workout snapshot or `weight_reps`. |
| `set_index` | Required numeric set index. |
| `set_id` | Optional planned set reference. |
| `weight`, `repetitions`, `duration_seconds`, `distance_meters`, `unit` | Optional metric fields according to result type. |
| `completed` | Required boolean. |

Result type shape:

| Result type | Meaning | Expected populated metrics |
| --- | --- | --- |
| `weight_reps` | Weighted strength set | `weight` and `repetitions` when logged; volume calculations apply here only. |
| `reps` | Repetition-only set | `repetitions`. |
| `duration` | Time-only set | `duration_seconds`. |
| `distance_duration` | Distance plus duration set | `distance_meters` and/or `duration_seconds`. |

Constraints:

- A backend upsert should identify a logical result by `owner_id`, `session_id`, `session_exercise_item_id` when present, and either `set_id` or `set_index`.
- `session_exercise_item_id` is optional for backwards compatibility, but new backend writes should preserve it when available.
- Result history queries must filter by owner, exercise, optional client, optional result type, completion state, and cutoff timestamp.

| Field | Requirement |
| --- | --- |
| `id`, `owner_id` | Required stable identity and tenant scope. |
| `exercise_id` | Required same-owner exercise reference. |
| `client_id` | Optional same-owner client reference. |

| `values` | Required numeric list. |

### `idempotency_keys`

Purpose: backend mutation replay protection required by Wave 9 API contracts.

Fields:

| Field | Requirement |
| --- | --- |
| `owner_id` | Required tenant scope. |
| `operation` | API operation name such as `sessions.start` or `results.upsertSetResult`. |
| `idempotency_key` | Required client-provided key. |
| `request_hash` | Recommended normalized request body hash to reject key reuse with different payload. |
| `response_status`, `response_body_ref` | Provider-specific storage for replayed response, or enough data to reconstruct it. |
| `created_at`, `expires_at` | Required lifecycle timestamps. |

Constraints:

- Unique `(owner_id, operation, idempotency_key)`.
- Reusing the same key with the same normalized request should return the original outcome.
- Reusing the same key with a different normalized request should fail as a conflict/validation error.
- Retention duration is blocked on production policy; do not store sensitive payloads unnecessarily.

## Query And Index Requirements

Recommended provider-neutral indexes:

| Query need | Recommended index |
| --- | --- |
| List clients by owner | `clients(owner_id, status, name)` or `clients(owner_id, updated_at)` depending on sort. |
| Get client by ID within owner | `clients(owner_id, id)`. |
| List active exercises | `exercises(owner_id, archived_at, name)`. |
| Enforce custom exercise active-name uniqueness | Unique normalized active name per `owner_id`, source/custom rules pending provider decision. |
| List workouts by owner/date/status | `workouts(owner_id, starts_at, status)`. |
| List workouts by client | `workouts(owner_id, client_id, starts_at)`. |
| Find latest draft | `workouts(owner_id, status, updated_at)` or explicit draft metadata. |
| Resolve active session | Unique/lookup index on `workout_sessions(owner_id)` where `status = 'active'`. |
| List completed sessions by client | `workout_sessions(owner_id, client_id, status, completed_at)`. |
| List results by session | `workout_results(owner_id, session_id, set_index)`. |
| Previous exercise performance | `workout_results(owner_id, exercise_id, result_type, completed)` plus join/index on session `completed_at` and `client_id`. |
| Quick value lookup | Unique `(owner_id, exercise_id, metric, client_id_or_null)`. |
| Idempotency replay | Unique `(owner_id, operation, idempotency_key)`. |

Pagination:

- Collection endpoints may use `next_cursor`.
- Cursor contents are provider-specific, but must preserve owner scope and stable sorting.

## Conflict And Error Expectations

The database/backend layer should support the API boundary's typed errors without leaking cross-owner data.

Expected cases:

- `not_found`: same response for missing ID or inaccessible other-owner ID.
- `validation`: malformed input, unsupported status transition, bad result metric shape, missing idempotency key.
- `conflict`: active session already exists for a different workout, duplicate active custom exercise name, stale update if optimistic concurrency is later added, or idempotency key reused with a different payload.
- `unauthorized` or `forbidden`: auth/session ownership failures once production auth exists.
- `cancelled`: request cancellation is supported at the API boundary; database writes that already committed must be replay-safe through idempotency.

## Migration Notes

Current app persistence is local AsyncStorage schema v2 with owner-scoped storage keys. A backend migration plan must be written later when provider/auth/account decisions exist.

Required migration properties:

- Preserve all existing entity IDs.
- Assign legacy local records to `local-trainer` until a product-approved sign-in migration maps them to a real owner/workspace.
- Do not clear old local data automatically on sign-in or logout.
- Do not move auth tokens into domain snapshots or backend domain tables.
- Preserve session/result snapshots so history remains stable after exercise rename/archive/edit.
- Validate same-owner references before upload or import.
- Decide whether first backend sync is one-way import, merge, or server-authoritative replacement before implementation.

Open migration questions:

- How does `local-trainer` data attach to a production account?
- Can one account own multiple workspaces?
- Can a trainer transfer clients/workouts between workspaces?
- What is the rollback plan if remote import partially succeeds?
- Are deleted/archived records retained, tombstoned, or purged under privacy policy?

## Privacy And Security Notes

- Client records may include personal contact, health, restriction, schedule, and performance information.
- Encrypt transport and storage according to the selected provider's production policy.
- Store auth credentials only through the credential policy selected for Wave 10 production auth; never in trainer domain records.
- Enforce least-privilege server access and deny cross-owner reads/writes by default.
- Avoid logging full client notes, restrictions, contact details, result payloads, tokens, or idempotency request bodies.
- Define retention, export, deletion, and audit requirements before production hardening.
- Use server-side timestamps for audit/lifecycle metadata where provider support allows; keep app-provided workout/session times as product data.
